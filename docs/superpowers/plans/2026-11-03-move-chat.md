# Move a chat: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** **Move to…** moves a chat between This PC and a paired machine (both directions), keeping its whole conversation, so that Claude on the target remembers everything.

**Architecture:**
- **The store.** Each service keeps a persistent, Threadgarden-owned Agent SDK `SessionStore` in its own database. A moved chat lives there on its target:
  - every turn of the chat resumes with `sessionStore`;
  - every read goes through `listSessions` / `getSessionInfo` / `getSessionMessages` with that store;
  - the indexer merges these chats into the normal history.
- **The move.** The desktop orchestrates it, calling each machine's service, because a remote holds no token back to This PC:
  1. check the source and the target;
  2. export the chat in parts from the source and import them on the target;
  3. commit on the target;
  4. mark the source copy as moved (hidden, read-only);
  5. move the scheduled sends;
  6. re-key the tab;
  7. send Claude's first note on the target.
- **Git.** Threadgarden runs only read-only git on the source. The rest of the git work is Claude's, told by the first note.

**Tech Stack:** TypeScript, Node 22, `@anthropic-ai/claude-agent-sdk` 0.3.314 (session store API, alpha), better-sqlite3 (the service db), zod (`packages/protocol`), SvelteKit 5 runes, Tauri 2 (the Rust protocol copy), vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-02-move-chat-design.md`, with the spike results `docs/superpowers/specs/2026-11-02-move-chat-spike-results.md`. The results win where they correct the design (§5's "writes its own transcript"). The spike tool `spikes/move-session/spike.ts` is a working example of every SDK call below. It is deleted in the last task.

## Global Constraints

- **Hard rule** (CONTRIBUTING.md): Threadgarden never writes, renames, moves or deletes anything under `~/.claude` (or `CLAUDE_CONFIG_DIR`). Moved chats live in the service's data dir db. `importSessionToStore` only reads.
- Only the official SDK API: `importSessionToStore`, `query({ resume, sessionStore, cwd })`, `listSessions` / `getSessionInfo` / `getSessionMessages` with `{ dir, sessionStore }`. Never parse `.jsonl`.
- **The session id is kept** across a move (spike). A chat is `{ machineId, sessionId }`; a move changes only `machineId`.
- **The store** answers `load` / `listSubkeys` for any `projectKey`, keyed by `sessionId` + `subpath`. The SDK asks with the target folder's key. Appends are deduplicated by `uuid`; entries without one are appended as they are.
- **Git on the source is read-only** (`status`, `rev-parse`, `rev-list`, `config --get remote.origin.url`). Threadgarden never clones, fetches, checks out, pushes, stashes or makes worktrees. Its only filesystem write is creating the target's missing parent folder, as New project does.
- **Protocol 9**, `REMOTE_PROTOCOL_RANGE = { min: 8, max: 10 }`. The Rust copy in `apps/desktop/src-tauri/src/service.rs` moves too. The capability is `'move'`. Move to… lists only machines whose service has it; an older one shows `Update ‹machine› to move chats there`.
- **No automatic moves.**
- **Copy, verbatim from the spec** (plus rulings R1–R7):
  - `3 changed files · 2 commits not pushed on fix/usage`
  - `This folder isn't a git repo; its files stay on ‹source›`
  - **Ask Claude to commit and push** · **Move anyway** · **Cancel**
  - `Starting ‹target›…`
  - `Moved to ‹target›`
  - `Update ‹machine› to move chats there`
  - `kumbal-machine's threadgarden is on main; 1 chat is running there`

### Rulings this plan makes (from the codebase maps)

- **R1. Turning a machine on is new code.** §3 check 3 says "as sending a message does today", but sending to an Off machine does not turn it on today.
  - The move calls `power.turnOn(id)`, then waits until `machines.get(id).status === 'on'`. The timeout is 10 min.
  - A machine without power control that is not On is refused: `‹target› is off`.
  - Cost if wrong: a later "send turns it on" feature may want to share this.
- **R2. The move is done once the target has committed the chat** (stored and listed).
  - Any failure before that leaves the chat where it was.
  - A failed source `markMoved` after the commit is retried by the desktop. Until then the dialog shows `The old copy on ‹source› is still shown`, with Retry.
  - A failed first note shows in the chat on the target with **Send again** (§6).
  - Cost if wrong: for a few seconds the chat shows on both machines.
- **R3. A lock while moving.** `move.exportBegin` locks the session on the source, and `chat.send` then answers `MOVING`. The lock ends with `move.markMoved` (the chat is away for good: `chat.send` answers `MOVED`), with `move.abort`, or after 10 min.
- **R4. The first note is a user message** whose first line is `[Threadgarden] This chat moved from ‹source› to ‹target›.`. The chat shows such a message with a small **Sent by Threadgarden** label, not as the owner's words.
- **R5. Forking a moved chat** (`forkSession` reads the local transcript) answers `Not available for a moved chat yet`.
- **R6. Moving a chat that is itself in the store** (moved before) exports from the store, not with `importSessionToStore`. Coming back to a machine that holds an away copy makes that copy store-backed and listed again: one chat (§6).
- **R7. Sends that wait for the limit reset** are re-created on the target with `whenLimitResets: true`, so they follow the target's own reset. Timed sends keep their `sendAt`.

## Review Focus

1. **A very long chat** (tens of MB of transcript) must move. Parts are at most 4 MiB, and the import holds parts until commit. Pinned in Task 6: a 9 MiB export moves in 3 parts and reads back equal.
2. **A turn starting between the check and the export.** `exportBegin` re-checks busy and locks. A `chat.send` during a move answers `MOVING`. Pinned in Tasks 4 and 6.
3. **The returning chat must not be the stale local copy.** On a machine that has both its own local transcript and the store copy of the same id, the list, `chat.open` and resume all use the store. Pinned in Task 3: a db with a local and a store copy of `s1` reads the store's 16 messages.
4. **The indexer's `removeVanished` must not delete store-backed chats**, and a full sync must not drop them. Pinned in Task 3.
5. **The target is Off with power control, then never comes up.** The move fails after 10 min with nothing changed, and the source is unlocked (`move.abort`). Pinned in Task 8.

### Task 8: The move, orchestrated on the desktop

**Files:**
- Create: `apps/desktop/src/lib/move/move-chat.svelte.ts`, `apps/desktop/tests/move/move-chat.test.ts`.
- Modify:
  - `apps/desktop/src/lib/state/tabs.svelte.ts`: `retarget(from: ChatRef, to: ChatRef)` swaps the key in place, keeps `active` and persists;
  - `apps/desktop/src/lib/projects.ts`: `supportsMove(m)`, like `supportsProjects`.

**Interfaces:**
- **Consumes:** Tasks 1, 6 and 7; `scopes.get(id).api`; `power.turnOn(id)`; `machines.get(id)`; drafts via `drafts.get` / `drafts.set` (key `sessionId`).
- **Produces** `class MoveChat`, constructed with `(app: { scopes, machines, power, tabs })`:
  - **`state`:** `'idle' | 'checking' | 'ready' | 'starting' | 'moving' | 'noting' | 'done' | 'failed'`, plus `check` (the source and target results), `problem: string | null`, and `oldCopyShown: boolean` (R2).
  - **`async prepare(ref: ChatRef, target: string, folder?: string)`** runs `move.check` on the source, and `move.target` when the target is On.
  - **`async run(opts: { moveAnyway: boolean })`** goes through these steps in order:
    1. turn the target on if it is Off (R1, 10 min, Review Focus 5);
    2. `move.target` again, if it wasn't run yet;
    3. `exportBegin`;
    4. the parts, exportPart → importPart;
    5. `commit`;
    6. the scheduled sends: list on the source, `scheduled.create` with the same id on the target (R7), then `cancel` on the source;
    7. `markMoved`, retried 3 times; when it still fails, `oldCopyShown` and a `retryMarkMoved()` (R2);
    8. copy the draft;
    9. `tabs.retarget`;
