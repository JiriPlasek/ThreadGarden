# v1.3 brainstorm — what needs the owner's decision

**Date:** 2026-10-31
**Status:** Proposals, not approved. Nothing here is built. Each section ends with the questions only the owner can answer.
**Context:** the owner asked which T3 Code (pingdotgg/t3code) features to adopt. The parts that were clear are specified in [the v1.3 design](2026-10-31-v1.3-design.md) and built. This document covers the rest. T3 Code facts come from reading its source at commit `53a986e` (2026-10-31).

## 1. Connecting machines ("boot up my old PC, connect it, control it from any other device")

**What T3 Code does.** Every server is an *environment* with a stable id. A client saves each machine as one environment with an ordered list of *routes* (LAN, Tailscale, public URL, SSH tunnel, a hosted relay). Before it sends a credential on a route, it checks a public descriptor (`/.well-known/…/environment`), so a LAN IP that now belongs to a different machine never gets the token. Pairing uses a single-use 12-character code that lasts 5 minutes. The code travels in a URL fragment (`https://host/pair#token=…`), is shown as a QR code, and is exchanged for an HMAC-signed session token with a 30-day lifetime and *scopes* (read, operate, terminal, filesystem write, …). The WebSocket uses short-lived tickets, so long-lived tokens never appear in socket URLs. Settings lists paired devices with revoke. Tailscale support shells out to `tailscale serve --https=443`. The hosted relay ("T3 Connect") is a Cloudflare Tunnel plus an account service. It has no mDNS discovery.

**Where Threadgarden stands.** The service already does what a remote target needs: it outlives the window, owns every session, and speaks one typed WebSocket protocol. Today it listens only on `127.0.0.1` with one bearer token from `service.json`. The UI already treats the service as a separate process. "Connect to another machine" is mostly about **reaching a service that is not local, safely**.

**Proposal (phased):**
- **Phase 1: one remote machine over Tailscale or LAN, paired by code.**
  - Settings → "Allow other devices" makes the service also listen on the machine's tailnet address. *Recommendation:* tailnet only by default, LAN as an opt-in, never on a public interface.
  - Pairing: "Pair a device" shows a one-time 12-character code and a QR code / link (`threadgarden://pair?host=…#code=…`) that lasts 5 minutes. The other Threadgarden enters it and gets a signed, revocable device token. Settings lists paired devices with **Revoke**.
  - The client has a **machine switcher** at the top of the places column ("This PC", "Old PC"). Each machine has its own projects, chats and Needs you list. Notifications from every connected machine are merged.
  - The protocol stays as it is, with a `hello` that names the machine and its capabilities. Every request already goes through one router, which makes it the natural place for scope checks.
  - Transport security: Tailscale already encrypts. For LAN we would need TLS with a self-signed certificate pinned at pairing (the client stores the certificate fingerprint from the QR code).
- **Phase 2: a headless install.** The old PC runs only the service (no window), started on boot. That needs an installable service mode (Windows service / launchd / systemd) and a CLI `threadgarden pair`.
- **Phase 3 (optional): a phone or browser client.** The UI is already a static SPA, so the service could serve it over HTTPS to a browser on the tailnet. A hosted relay like T3 Connect is a product and infrastructure of its own; *recommendation:* do not build it.

**Risks.** A remote client can run code on the target machine: every agent can run shell commands. Pairing must be explicit, scoped and revocable, and the service must refuse remote connections unless the owner turned them on. Remote file paths (`@` mentions, dropped images) need to be uploaded rather than passed as local paths. Claude Code's own login happens on the target machine.

**Owner questions:**
1. Which network do you use between your machines: Tailscale, the same LAN, or something else? This decides phase 1's transport.
2. Should the old PC be a full Threadgarden install (window and all) or a headless "service only" box?
3. Should a connected device have full control (send, approve permissions, stop), or should there also be a read-only "watch" pairing?
4. Is a phone or browser client in scope, or only Threadgarden desktop ↔ Threadgarden desktop?

## 2. Pull request management

**What T3 Code does.** It uses the GitHub GraphQL and REST APIs directly. The token comes from settings, `GH_TOKEN`, or `gh auth token`. It has a PR list page; commit, push and create PR from a thread, with an LLM writing the title and body; review with diffs, line comments and reviewer requests; merge and auto-merge; checkout into a worktree; PRs linked to the thread that created them; and an agent tool that watches CI and reviews and wakes the agent.

**Proposal (smallest useful slice first):**
- **Slice A: PRs per project, read-only.** A "Pull requests" section in a project's view lists open PRs for the repository (author, state, checks, review state, updated). It uses `gh` for the token and API calls (`gh pr list --json …`), so there is no token handling of our own, and it refreshes on demand and every few minutes. Clicking a PR opens it in the browser or **Start a chat about this PR** (a new chat in the project with the PR's number, title and diff summary as the first message).
- **Slice B: link PRs to chats.** When a chat's agent runs `gh pr create`, the PR URL is detected from the tool output and shown in the chat header and on the chat row with its live checks/review state.
- **Slice C: actions.** Checkout (worktree), merge, close and request review from Threadgarden. This is where most of T3 Code's surface lives; *recommendation:* only after A and B prove useful.

**Owner questions:**
1. Is your work on GitHub only, or also GitLab / Azure DevOps (work repos)?
2. What do you do with PRs most: watch CI and reviews for PRs your agents opened, or review other people's PRs?
3. Is depending on the `gh` CLI acceptable (it must be installed and signed in), or should Threadgarden hold its own token?

## 3. Viewing and writing project code

**What T3 Code does.** A file tree and an editable file view with autosave, a diff pane (per turn, against a branch, per commit) with inline review comments, and many file previewers. It uses neither Monaco nor CodeMirror; it uses `@pierre/diffs`.

**Proposal:**
- **Slice A: read-only file browser.** A "Files" panel per project, next to the chat or as a tab: a file tree that respects `.gitignore` (the `@` file index already walks it), and a viewer with Shiki highlighting (already a dependency). Clicking a path in a tool call or diff opens it there. This is cheap and has no risk to the user's files.
- **Slice B: changes view.** `git status` / `git diff` of the project working tree, grouped by file, using the existing diff renderer, with "Changes in this chat" (files the chat's Edit/Write calls touched).
- **Slice C: editing.** An editor (CodeMirror 6 is the light, accessible choice) with explicit save, conflict detection when the agent edits the same file, and undo. Editing is where data-loss risk lives (an anti-goal), so it needs its own careful design.

**Owner questions:**
1. Is the goal to *look* at code while you chat (A and B), or to replace opening an editor (C)?
2. If editing: quick fixes in one file, or real multi-file work? Should "Open in VS Code / your editor" be enough?

## 4. Usage: follow-ups to what v1.3 built

v1.3 builds a usage meter and dialog from the SDK's `rate_limit_event` and the experimental `get_usage` call. It also builds scheduled sends: "Send when the limit resets". T3 Code goes further in three ways:
- **API-equivalent cost** from transcripts priced with LiteLLM's public price table, labelled "not your bill". Threadgarden can only read transcripts through `getSessionMessages`, which the v1.3 analytics already do, so per-model token totals exist and pricing them is a small addition. **Question:** do you want an estimated cost column ("what this would cost on the API")?
- **Auto-resume at reset:** a chat stopped by the limit gets "Continue where you left off." sent automatically when the window reopens, as a per-chat choice or a global default. v1.3's scheduled send covers this manually. **Question:** should this be automatic (a setting), or is the manual "Send when the limit resets" enough?
- **"Snooze until reset":** a limited chat moves to On hold until the reset. This is easy on top of v1.2 holds. **Question:** wanted?

## 5. Analytics: follow-ups

v1.3 builds activity, tokens by model, projects, tools, subagent types, a weekday × hour heatmap, and "topics" as the most frequent words in chat titles. Real topic grouping, such as clustering chats by what they are about, needs a model call per chat (Claude Code's `haiku`, the same way titles are generated) and so costs tokens. **Question:** worth it, and should it be opt-in?

## 6. Rebrand: the internal names

v1.3 renames everything a user sees to **Threadgarden** and ships the new icon. These internal names were kept on purpose, because changing them moves or orphans data a user already has: the npm scope `@pahub/*`, the Tauri identifier `dev.pahub.desktop` (it decides the app's data folder and the Windows/macOS registration), the data dir and `pahub.db`, the `pahub.` WebSocket subprotocol, the `PAHUB_*` environment variables and the repository name. A full rename is one release with a migration: copy the data dir to the new location on first start, keep reading the old one as a fallback for one version, then rename the package scope and environment variables, with the old names accepted for one version. The repository rename is yours to do on GitHub.

**Owner questions:**
1. Rename the internals too (one migration release), or keep them as they are?
2. Rename the GitHub repository to `threadgarden`?
