## 1. Owner requests (verbatim intent)

1. The Activity panel sorts agents and processes by activity: running ones always on top, then the finished ones by when they finished.
2. The Activity panel button is one global state: on shows it on every chat, off hides it everywhere.
3. See the model of running agents, and more details about the agents running in a chat.
4. A usage monitoring view (adopted from T3 Code).
5. When a usage limit is reached, an option to schedule a message so it is sent once the limit resets.
6. Thread analytics: statistics of usage, agents, topics — graphs.
7. Icons for projects, taken from the project's favicon.
8. More theme settings.
9. Rebrand to **Threadgarden**, with the owner's new logo as the app icon.

## 2. Activity panel (items 1–3) — work package A

**Sort.** In both sections (Agents, Processes): tasks that have not ended (pending, running, paused, unknown) first, newest start first; then ended tasks, most recently ended first. The end time is `endedAt`, else `startedAt + durationMs`, else `startedAt`. A pure, unit-tested comparator.

**Global toggle.** `settings.activityOpen` alone decides whether the side column shows, on every chat: the per-chat `hadTasks` / `activityRequested` gating goes. A chat without tasks shows the existing empty-state text. Ctrl/Cmd+. and the header button flip the global state. *(Builder's call)* the narrow-pane overlay drawer stays a per-view, manual drawer: a drawer that covers the chat on every chat switch would get in the way.

**Agent details.**
- **Model.** Each agent task carries `model` when known: first the `model` input of the Agent tool call that started it (`toolUseId`), else the `message.model` of the first assistant message streamed with `parent_tool_use_id` equal to that `toolUseId`; later subagent messages update it if it changes. Shown on the row (short form, e.g. `opus-4` style labels are not invented: show the alias or the model id as given, trimmed of a `claude-` prefix). When unknown, show nothing (do not guess "inherits").
- **Expandable details.** An agent row can be expanded (a disclosure button; keyboard accessible) to show: the prompt it was given (`task_started.prompt`, clamped, with "Show all"), subagent type, model, started at, duration, tokens, tool uses, last tool, the progress summary, background/foreground, the workflow name for workflow tasks, and its error when it failed. Processes expand the same way (command/description, type, timings, summary, error).
- **Nesting.** A task whose `parentTaskId` names another task in the list is shown indented under its parent (one level of indent per depth, capped at 3); sorting applies among siblings.
- Protocol: `ChatTask` gains optional `model`, `prompt`, `spawnDepth`, `workflowName`. All optional, so older services and clients interoperate.
- Not in scope: live process output. The CLI has a `get_task_output` control request but the SDK's `Query` does not expose it; revisit when it does.

## 3. Usage and scheduled sends (items 4–5) — work package B

**Source of truth** (no scraping, no private endpoints):
- `rate_limit_event` messages streamed by every live session (`rate_limit_info`: `status` allowed / allowed_warning / rejected, `resetsAt`, `rateLimitType`, `utilization`, overage fields). The service keeps the latest info per `rateLimitType`, account-wide (they are the same account for every chat), persisted in `pahub.db` so it survives restarts, with the time it was observed.
- When a live session exists, the SDK's experimental `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET({ skipBehaviors: true })` on demand (the usage view is open, at most once a minute). It is feature-detected and wrapped: any failure or shape mismatch falls back to the rate-limit events. Its answer is parsed leniently (unknown fields ignored, missing ones tolerated). pahub never starts a Claude process only to read usage.
- API-key / Bedrock / Vertex users: `rate_limits_available: false` → the view says plan limits do not apply.

**UI.** A compact usage meter in the bottom agents strip (the 5-hour window's percentage and reset time; amber at warning, red when rejected; hidden when nothing is known). Clicking it, or "Usage" in Ctrl/Cmd+K, opens a **Usage** dialog: one bar per known window (5-hour, 7-day, 7-day per model, overage/extra usage), each with its utilization, reset time ("resets in 2 h 14 min, at 15:00") and when it was last observed; subscription type when known.

**Scheduled sends.**
- When a chat's turn is refused because of a usage limit (an assistant message with error `rate_limit`, or a `rate_limit_event` with status `rejected`, for that chat), the chat shows a notice "Usage limit reached — resets at 15:00" and the composer offers **Send when the limit resets** next to Send.
- The composer's send button also gets a small menu: **Schedule send…** (pick a time: presets "When the limit resets" when known, in 1 h, tomorrow 9:00, custom).
- A scheduled send is stored by the service in `pahub.db` (`scheduled_sends`: id, session id, text, attachments as the composer would have sent them, send_at, created_at, state) and fires at `send_at` (+30 s margin after a limit reset) through the same path as `chat.send`, resuming the chat when it is not live. Several scheduled sends of one chat go out in order, one per turn.
- If the limit is still refused when it fires, it is rescheduled to the new reset time once; after that it stays pending with an error the user can retry.
- Scheduled sends are listed in the chat above the composer (text preview, time, **Send now**, **Edit** (back into the composer), **Cancel**), and a chat with one counts as having pending work: it shows a clock badge in lists. The service does not exit on idle while a scheduled send is pending. A send whose time passed while the service was not running fires at the next service start (and says it was late).
- A notification "Scheduled message sent to ‹title›" is posted when it goes out (respecting the notifications setting).

## 4. Analytics (item 6) — work package C

**Data.** Per-session statistics extracted while indexing, from the same `getSessionMessages` walk the indexer already does (no transcript parsing, read-only): per day (local date) and model: user messages, assistant messages, input / output / cache-read / cache-creation tokens (from assistant `message.usage`); per tool name: call count; per subagent type: Agent tool calls; first and last message time. Stored in new pahub tables keyed by session, replaced on re-index. Sessions already indexed get their statistics in a **background backfill** after the regular index pass, a few sessions at a time with event-loop yields, without redoing full-text indexing; a budget test keeps it from slowing the index or the UI.

**View.** An **Analytics** view, opened from the places column (below Running) and from Ctrl/Cmd+K, shown in the main pane like a chat tab. Controls: range (7 days, 30 days, 90 days, all time) and project (all or one). Content:
- KPI tiles: chats, messages, output tokens, active days, busiest project.
- Activity over time: messages per day (bars), with chats started as a line.
- Tokens per day stacked by model.
- Top projects (horizontal bars, click filters to that project).
- Tools used (top 10) and subagent types (top 10), horizontal bars.
- When you work: weekday × hour heatmap.
- Topics *(builder's call)*: the most frequent meaningful words of chat titles in the range (stop-words removed), as a ranked list. Real topic modelling is left to the brainstorm.
Charts are plain SVG Svelte components (no chart dependency), accessible (titles, `<desc>`, tables behind a "Show data" toggle), and follow the light/dark tokens and the dataviz skill's palette guidance. Cost in dollars is not shown (transcripts carry no reliable cost).

## 5. Project icons (item 7) — work package D

The service looks for an icon in the project folder, in order: `<link rel="icon">` / `apple-touch-icon` in `index.html`, `public/index.html`, `src/index.html`, `src/app.html`; then fixed paths: `favicon.svg|ico|png`, `public/favicon.*`, `static/favicon.*`, `app/favicon.ico`, `app/icon.*`, `src/app/favicon.ico`, `src/app/icon.*`, `assets/icon.*`, `icon.png`, `logo.svg`, `public/logo.*`, `src-tauri/icons/icon.png`, `.github/logo.*`; then the same fixed paths one level into `apps/*` and `packages/*` (monorepos). Only regular files under the project folder (no symlink escape), at most 512 KB, image types only (by extension and magic bytes). A new request `projects.icon {projectId}` returns a data URL or null; the result is cached per project and refreshed when the file's mtime changes or every 10 minutes. The UI requests icons lazily for visible projects and shows them as 16 px rounded images in the project list, the chat header and the quick switcher. A project without an icon gets a letter tile (first letter of its name, colour from a hash of the project id). *(Builder's call)* no manual icon override in v1.3.

## 6. Themes (item 8) — work package E

New appearance settings (protocol `Settings`, all optional with defaults matching today):
- **Accent colour:** Blue (today's), Teal, Green, Violet, Rose, Amber, Graphite. Drives `--primary`, `--ring` and the focus/selection tokens in both themes.
- **Dark style:** Default, Dim (softer grey), Midnight (true black, for OLED).
- **Light style:** Default, Warm (paper-tinted background).
- **Interface font:** Inter (bundled, today's) or the system font.
- **Code font:** default monospace stack or a custom family name.
A live preview in the Settings dialog's Appearance section. Applied as data attributes / CSS variables on the root, next to `data-theme`, without a reload.

As built: settings `accent`, `darkStyle`, `lightStyle`, `uiFont`, `codeFont` (string or null); unknown stored values read as the default. Tokens in `apps/desktop/src/routes/themes.css`; a unit test checks WCAG AA for every theme × style × accent from the real stylesheets.
- *(Builder's call)* The look before v1.3 is not blue: its primary, ring and selection tokens are shadcn's neutral greys (only links and the "your turn" dot are blue). The default accent is therefore **Graphite**, exactly today's values, and **Blue** is a real blue. The list of seven names is unchanged.
- *(Builder's call)* The default light look has one pre-existing AA shortfall: muted text (`oklch(0.556 0 0)`) on the muted grey (`oklch(0.97 0 0)`) is 4.34:1. It stays, since the defaults must not change; the test pins it. Darkening the default muted text to about `oklch(0.53 0 0)` would fix it, at the cost of a visible change. With a colour accent the light theme's muted text is `oklch(0.5 0 0)`, so all other combinations pass.
- *(Builder's call)* Colour accents also tint the selection token (`--accent`: selected rows, menu highlight) by mixing the primary into the background; graphite keeps the neutral grey.
- *(Builder's call)* The code font is a free-text family list, sanitised to letters, digits, spaces and `_-.` (up to four names of 64 characters), each quoted, with the default monospace stack behind it.
- The settings are cached in `localStorage` and applied by `app.html` before the first paint, the theme included (which also removes the light flash a dark-theme user saw at start before v1.3).

## 9. Internal rename and migration — work package G (owner decision, 2026-10-31)

The owner answered the brainstorm's §6: rename the internals too, in this release, with a migration, and rename the GitHub repository. This supersedes §7's second bullet. Historical design docs keep the names they were written with.

**Rename map.**

| Before | After |
| --- | --- |
| npm scope `@pahub/*`, root `pahub-workspace` | `@threadgarden/*`, `threadgarden-workspace` |
| Cargo crate `pahub`, lib `pahub_lib` | `threadgarden`, `threadgarden_lib` |
| Tauri identifier `dev.pahub.desktop` | `dev.threadgarden.desktop` |
| Node sidecar `pahub-node` | `threadgarden-node` |
| Data dir `…/pahub` (`%APPDATA%`, `~/Library/Application Support`, `$XDG_DATA_HOME`) and `pahub.db` | `…/threadgarden` and `threadgarden.db` |
| OS keychain service `pahub` | `threadgarden` |
| WebSocket subprotocol `pahub.<token>`, hello client `pahub-desktop` | `threadgarden.<token>`, `threadgarden-desktop` |
| `PAHUB_*`, `VITE_PAHUB_*`, `__PAHUB_API_KEY_ONLY__` | `THREADGARDEN_*`, `VITE_THREADGARDEN_*`, `__THREADGARDEN_API_KEY_ONLY__` |
| localStorage keys, symbols, temp-dir prefixes, type names (`PahubTitles`) | the same with `threadgarden` |

**What must keep working (anti-goal: never lose work).**
- **Data.** At start, before it takes its lock, the service migrates once: when the new data dir has no `threadgarden.db` and the old dir has a `pahub.db`, it copies the database with SQLite `VACUUM INTO` to a temporary name in the new dir, then renames it to `threadgarden.db` (crash-safe; a half-done copy is never used). The old dir is left as it was, plus a short `MOVED-TO-THREADGARDEN.txt` saying where the data went and that the folder can be deleted. Logs, `service.json` and the lock are not copied. With a data dir override (`THREADGARDEN_DATA_DIR`, or the legacy `PAHUB_DATA_DIR`), the same applies inside that one dir (`pahub.db` → `threadgarden.db`).
- **An old service still running.** If the old dir's lock is held, the new service does not migrate and does not start on an empty database: it exits with a clear error ("an older pahub service is still running…"). The desktop shell looks for `service.json` in the new dir first, then in the old one; an old service found there is connected to (the client offers both subprotocols), its `hello` reports the old protocol, and the existing "restart the service" flow stops it and starts the new one, which then migrates. `PROTOCOL_VERSION` becomes 4.
- **API key.** Reading the key looks under `threadgarden` first, then under `pahub`; a key found under the old name is written under the new one and then deleted under the old one. Saving or removing the key also removes any old entry.
- **Legacy names accepted for one release:** `PAHUB_DATA_DIR` and the `PAHUB_API_KEY_ONLY` build flag (each logs a deprecation note), the `pahub.` subprotocol on the service side. Dev-only variables (mock, e2e, perf, real-suite) are renamed outright, CI included.
- **Not migrated:** the webview's own storage (it follows the Tauri identifier; the only thing in it, the appearance copy, is rebuilt from the service's settings on first connect), the OS notification and start-on-login registrations (re-made under the new name; the README says to uninstall the old "pahub" app and turn start-on-login on again if it was on).

**Docs.** README gets an "Upgrading from pahub" note (what moves, what to uninstall), the "keeps the old name" sentence goes, and every path, variable and command in README, CONTRIBUTING, the package READMEs and docs/architecture.md uses the new names. Tests cover the migration (fresh install, old db only, both present, old service lock held, override dir, a failed copy leaving no `threadgarden.db`), the keychain fallback (unit-testable part), and dual subprotocol acceptance.
